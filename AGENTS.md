# Prada Sound — инструкции агентам

## Текущий этап: Single-file MVP
По указанию пользователя логика лобби и WebSockets живёт целиком в
backend/app/api/lobby.py, состояние — в Python-словаре LOBBIES в памяти.
В main.py только подключение роутера. На этом этапе не подключать БД,
не создавать repository/service/schema-файлы для комнат и не реализовывать
версии, транзакции, lease или snapshot-протокол из будущего плана ниже.
Один процесс; рестарт теряет комнаты. Приоритет — компактный работающий код.
Эти указания имеют приоритет над противоречащими разделами ниже.
Frontend текущего этапа: вся логика входа/лобби/WebSocket в frontend/src/App.tsx.
Без роутера, Redux, UI-библиотек и разбиения на компоненты/хуки по файлам.
Допускаются только необходимые служебные файлы React/Vite/TypeScript.
Текущий протокол: сервер хранит tracks_queue (список YouTube Video ID) в Lobby.
Main и Members равноправно добавляют add_track; lobby_state с полной очередью
рассылается всем, включая отправителя. Никаких заявок/одобрений и логов вместо
очереди. Первый элемент — текущий трек. Только Main рендерит YouTube iframe
и отправляет skip_track, удаляющий первый элемент. playback_revision растёт
на skip, чтобы перезапускать даже повтор одного видео; append не прерывает плеер.
Яндекс текущего этапа: пользователь подключает аккаунт через device code.
Сервер временно хранит его токен по случайному непрозрачному handle; сам токен
не передаётся в WebSocket и другим участникам. При добавлении yandex_<ID>
очередь сохраняет handle автора на сервере, но не рассылает его в lobby_state.
Только Main запрашивает аудиоссылку по ID элемента очереди и host_token;
сервер получает её через аккаунт автора трека. Main не обязан подключать свой
Яндекс, если воспроизводит треки гостя. При истечении доступа автор подключает
аккаунт заново, а очередь обновляет только его элементы. Сервер не скачивает
и не проксирует MP3; браузер Main получает прямую ссылку провайдера.

## Цель и границы
Создать сервис совместной очереди музыки. Main создаёт лобби и один
воспроизводит музыку на своём устройстве; Members входят по ссылке/QR,
ищут треки и добавляют их в очередь. Сервер передаёт только метаданные,
команды и состояние. Аудио идёт от провайдера напрямую к Main.
Не реализовывать серверное скачивание, хранение, транскодирование аудио.
Для Яндекс-треков сервер использует авторизацию добавившего участника для
получения аудиоссылки. Main воспроизводит её на своём устройстве без входа
в Яндекс Музыку. Эта схема требует действующего доступа автора трека.

## Приоритет MVP
Делаем функциональный, быстрый локальный MVP с простым запуском на одном VPS.
Приоритет: удобный вход по QR, поиск, импорт, надёжная очередь и плеер Main.
Максимум 100 одновременно активных лобби, обычно 50–100 человек в каждом:
целевой диапазон 5000–10000 соединений. Это цель проверки, не обещание ёмкости.
20000 соединений — необязательный стресс-сценарий, а не требование релиза.
При одном соединении на участника 100 лобби по 100 человек дают максимум
10000 соединений; дополнительные вкладки не увеличивают лимит участников.
Не проектировать кластер, микросервисы и распределённую доставку заранее.
Сначала рабочие пользовательские сценарии, затем измерения и точечные правки.

## Стек
- Python 3.12+, FastAPI, Uvicorn: один процесс на начальном VPS.
- PostgreSQL, SQLAlchemy 2 async + asyncpg, Alembic, Pydantic 2.
- React, TypeScript strict, Vite; статическая сборка через Caddy.
- REST для команд и snapshot; native WebSocket для событий.
- httpx.AsyncClient с общим пулом; yandex-music ClientAsync в адаптере.
- pytest, Ruff, mypy; Vitest, Playwright; k6 для нагрузки.
- Redis, Celery, Kafka, SSR и Kubernetes в MVP не добавлять.
- Модульный монолит; WS-подписки и рассылка в памяти одного процесса.
  Рестарт восстанавливается из PostgreSQL через snapshot/reconnect.
- Для локальной разработки достаточно приложения и PostgreSQL;
  Caddy нужен для опубликованного HTTPS-входа. Сборку frontend делать вне VPS.
- Версии зависимостей закреплять lock-файлами после проверки совместимости.

## Роли и владение файлами
Все субагенты используют GPT-6 Sol: model = gpt-6-sol.
При явном выборе модели для запуска указывать именно gpt-6-sol.
Не заменять недоступную модель молча: сообщить о блокировке.
Архитектор назначает роль, задачу, разрешённые пути и критерии приёмки.
Не более трёх субагентов одновременно; четыре роли выполняются волнами.
Роли — зоны ответственности, а не требование запускать четырёх агентов.
Небольшие задачи выполнять одним агентом; делегировать только независимые
существенные подзадачи. Не расходовать ресурсы на дублирующие обзоры.
Не запускать вложенные делегации. Один файл изменяет один агент.

| Роль | Владение | Ответственность |
| --- | --- | --- |
| Архитектор | docs/, contracts/, infra/, корневые конфиги и lock-файлы | Контракты, решения, сборка изменений, ресурсный бюджет |
| Backend | backend/app/main.py, backend/app/settings.py, backend/app/api/, backend/app/schemas/, backend/app/domain/, backend/app/db/, backend/migrations/, backend/tests/domain/ | Инициализация FastAPI, настройки, лобби, сессии, роли, очередь, транзакции, REST |
| Frontend | frontend/ | UI Main/Members, QR, поиск, очередь, OAuth UX, плееры только у Main |
| Streaming | backend/app/providers/, backend/tests/providers/ | Поиск, импорт, OAuth, доступность треков, квоты, адаптеры |
| Real-time | backend/app/realtime/, backend/tests/realtime/, tests/load/ | WS, рассылка, переподключение, backpressure, нагрузочные сценарии |

Изменения вне зоны владения согласовать с архитектором.
Streaming задаёт контракт плеера; Frontend реализует браузерную часть.
Real-time вызывает доменный сервис Backend, не дублирует логику очереди.

## Интеграции
- YouTube: Data API/oEmbed для метаданных; видимый IFrame Player у Main — резерв.
  По явному поручению пользователя разрешён экспериментальный аудиорежим
  на VPS: yt-dlp через отдельный VPN-прокси, поток без записи на диск.
  Маршрут извлечения и загрузки аудио должен совпадать; доступ только Main.
  Настройка YOUTUBE_AUDIO_ENABLED включается явно. Яндекс идёт напрямую.
  Не обещать импорт всей библиотеки YouTube Music через YouTube Data API.
- SoundCloud: зарегистрированное приложение, OAuth с PKCE для импорта,
  app credentials для публичного поиска; Widget или разрешённый stream.
  Проверять playable/preview/blocked и региональные ограничения.
- Яндекс Музыка: обязательный экспериментальный адаптер yandex-music.
  Флаги YANDEX_IMPORT_ENABLED и YANDEX_PLAYBACK_ENABLED выключены по умолчанию.
  Для включения playback проверить полный трек с аккаунтом Main,
  срок жизни URL, доступ из браузера Main, CORS/Range и смену трека.
  Не считать preview полноценным воспроизведением. Если прямой поток
  недоступен, вернуть unsupported; не добавлять скрытый аудиопрокси.
  Импорт/метаданные не означают готовность обязательного playback.
- Apple Music: опционально, MusicKit; доступ и подписку проверять у Main.
- Анонимный участник не обязан авторизоваться в стриминге, но приложение
  может требовать credentials провайдера. Не обещать поиск без квот.
- Импортировать выбранные треки постранично, максимум 500 за операцию.
- Смена провайдера или подбор альтернативы требуют подтверждения пользователя.
- У каждого адаптера: search, resolve_metadata, import_library,
  playback_descriptor; capabilities объявлять явно.
- TrackRef: provider, provider_track_id, title, artists, duration_ms,
  canonical_url, artwork_url, availability. В очереди нет токенов/stream URL.
- playback_descriptor возвращать только Main непосредственно перед стартом.
- Таймауты, ограниченная конкуренция, Retry-After, backoff и circuit breaker.
  Ошибка одного провайдера не должна ломать всё лобби.

## Состояние и протокол
- PostgreSQL — источник истины: lobby, membership, queue_item,
  playback_state, provider_credential, command_deduplication.
- Любая мутация: проверка сессии/роли, транзакция, блокировка строки lobby,
  проверка expected_version, изменение, увеличение version, commit.
  Сетевые запросы к провайдерам не выполнять под блокировкой БД.
- command_id уникален в рамках лобби. Повтор возвращает прежний результат.
  Несовпадение expected_version возвращает conflict и актуальную version.
- Событие: protocol_version, lobby_id, version, type, payload.
  События публиковать после commit; не заявлять exactly-once delivery.
- При входе сначала зарегистрировать ограниченный буфер WS, затем прочитать
  согласованный snapshot. Удалить события <= snapshot.version и применить
  оставшиеся по порядку. При разрыве последовательности запросить snapshot.
- Дубликаты событий игнорировать. После reconnect всегда получать snapshot.
  Heartbeat передаёт текущую version для обнаружения пропущенного события.
  Heartbeat раз в 30 секунд с jitter; не читать БД для каждого соединения.
  Версию комнаты обновлять в памяти после commit; подписчиков хранить по lobby.
  Reconnect с exponential backoff и jitter; рассылка только участникам комнаты.
- Только Main управляет play/pause/seek/skip/reorder/remove.
  Members добавляют треки. Эти права проверяются сервером на каждом действии.
- Для Main использовать playback lease и fencing generation; устаревшие
  вкладки не могут менять playback. Потерявшая lease вкладка останавливается.
- При disconnect Main гости не становятся хостами автоматически.
  Новые старты приостановить; после reconnect сверить реальный плеер Main.
- ended содержит queue_item_id и playback generation; повтор не пропускает
  следующий трек. Недоступный трек получает явную причину отказа.
- Нет секундной рассылки позиции: timestamp + position + состояние;
  позиция отображается локально, изменения приходят по событиям.
- Main нажимает «Начать» для разрешения autoplay. Обрабатывать блокировку
  autoplay, фоновые ограничения браузера и ошибки внешних плееров.

## Ресурсы и безопасность
- VPS: 1 vCPU, 4 GiB RAM, 15 GiB SSD. Настройки приложения — в .env.example;
  это отдельные настройки от config.toml среды Codex.
- Начальные настраиваемые пределы: 100 активных лобби, 100 участников
  включая Main на лобби, 10000 WS на инстанс, 500 треков в очереди.
  Эти пределы ограничивают приём, а не подтверждают производительность.
  Проверять лимиты атомарно; лишние соединения отклонять до регистрации.
  Учитывать все вкладки в общем WS-лимите; одна активная WS-сессия на
  membership, переподключение заменяет предыдущую. Не держать пустые лобби
  активными до истечения срока хранения: освобождать слот после 5 минут
  отсутствия соединений; повторная активация тоже проверяет лимит лобби.
- DB pool: 5 соединений, max_overflow=5. Не держать соединение на каждый WS.
- WS: входящие сообщения <=16 KiB; исходящий буфер <=16 KiB на клиента,
  общий бюджет исходящих буферов <=64 MiB на процесс, память выделять лениво.
  Ограничивать также внутренние очереди WS-библиотеки, отключить WS-сжатие
  по умолчанию; транспортные буферы учитывать при измерении памяти.
  Медленных клиентов отключать с требованием resync; snapshot через REST.
  Один payload сериализовать один раз на комнату; не копировать полную очередь
  для каждого подписчика. В событии только изменение, большие данные через REST.
- Общий ограниченный TTL-кеш метаданных <=64 MiB; персональные данные
  изолировать по владельцу. Учитывать правила хранения каждого провайдера.
- Ограничивать частоту поиска/добавления по сессии, лобби и IP;
  учитывать общий NAT у гостей. Поиск с debounce и лимитами провайдера.
- Lobby TTL: 24 часа после последней активности. Очистка малыми батчами;
  ротация логов, контроль WAL/диска, резервные копии вне VPS.
- Секреты только в окружении; credentials в БД шифровать AEAD с внешним
  ключом. Не логировать токены, cookies и подписанные URL.
- OAuth: state, PKCE где поддерживается, минимальные scopes, отзыв/удаление.
  Не запрашивать пароль стриминга или экспорт полной браузерной сессии.
- Сессии: Secure/HttpOnly/SameSite cookies; проверять Origin для WS,
  CSRF для REST-мутаций. Invite-код не предоставляет права Main.
- URL валидировать по провайдеру/ID; защищаться от SSRF и редиректов
  в приватные сети. Никакого универсального серверного URL-fetch endpoint.

## Порядок работы и приёмка
1. Архитектор фиксирует REST/WS/Provider контракты в contracts/ и ADR в docs/.
2. Проверить реальные возможности YouTube, SoundCloud и Яндекса на тестовых
   аккаунтах; mocks не являются доказательством работоспособности API.
3. Реализовать вертикальный сценарий: Main создаёт лобби, Member добавляет
   трек, Main воспроизводит, очередь синхронизируется и переживает reconnect.
4. Добавить импорт и отказоустойчивость провайдеров.
5. Проверить права, гонки добавлений, идемпотентность, двойной ended,
   потерю событий, рестарт сервера, медленного клиента и утечку credentials.
6. Сначала короткий smoke на 1x100; после готовности сценариев k6 с отдельной
   машины: 10x100, 100x50, затем 100x100. Остановить рост при насыщении,
   сохранить результаты; не тратить время на стресс до готовности функций.
   Базовый профиль: одна мутация очереди на лобби каждые 10 секунд,
   один поиск на лобби каждые 5 секунд, playback update раз в 30 секунд.
   Распределять запросы во времени. Провайдеры в capacity-тесте — stubs;
   квоты и реальный поиск проверять отдельно малым числом запросов.
   Затем короткий burst добавлений и reconnect 10% клиентов с jitter.
   Измерить RSS, CPU, event-loop lag, DB pool, p95 команд и WS delivery.
   Цели: p95 команд без внешнего API <300 мс, commit-to-delivery <500 мс,
   RAM всего VPS <3 GiB. Часовой soak только на выбранном рабочем профиле.
   Это критерии, не результаты. 20000 попыток соединения — опциональный тест
   корректного отказа сверх лимита; не требовать обслуживания всех 20000.
7. Если 5000–10000 соединений не укладываются в VPS, показать измеренное
   ограничение и настроить admission limit под него. Сначала устранить
   конкретные узкие места или предложить больший VPS. Redis, несколько
   воркеров, outbox и кластер не реализовывать в рамках текущего MVP.

Работать автономно в назначенной зоне, сохранять чужие изменения.
Не добавлять зависимости без необходимости. Не деплоить и не менять
production-данные без явного поручения. Не коммитить секреты.
В отчёте: изменённые файлы, проверки, реальные результаты и блокировки.
Отсутствие API-ключа обозначать как непроверенную интеграцию, не как успех.
